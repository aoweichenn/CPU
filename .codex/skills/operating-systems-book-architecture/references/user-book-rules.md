# 《操作系统第一册》用户硬性规则

每次触发 `operating-systems-book-architecture` 都要完整读取本文件。以下规则来自用户对本书的持续要求，不依赖会话记忆。

## 内容深度与章节规模

- 全书的逻辑起点必须是一台“只有硬件、没有操作系统”的机器。先说明它怎样装入并运行一个任务、硬件此时能提供哪些最小状态，再用具体失败推动后续设计。
- 每次演进只解决一个核心失败，并让这个新机制形成一章。下一章必须明确继承上一章已经得到的机器状态，再从尚未解决的问题继续；不得按现代子系统名词直接切章。
- 涉及处理器现场、特权、异常、时钟、地址转换、存储或设备时，先解释当前推导真正依赖的硬件抽象及可观察状态，再引入操作系统结构。硬件说明服务于本次演进，不扩展成脱离问题的硬件百科。
- 面向零基础读者，从一次具体操作、限制、矛盾或失败开始推导；先让读者看见“原做法为什么不够”，再引入名称、对象和机制。
- 章节开头不得先展示完整链路、对象总图或术语全景。先推导一个局部问题和一个必要结构；只有所有参与对象都已分别建立后，才用完整链路做综合验证。
- 任何概念首次出现时都要解释：它要解决什么问题；如果没有它会发生什么；它保存哪些状态；这些状态为什么必须分开；谁创建、持有、修改、释放或恢复它。
- 不用术语列表代替推导，不用结论代替过程，不以“显然”“容易知道”“以此类推”跳过关键因果。
- 每章正文以成品 PDF 中至少约 50 个有效正文页为基线；主题需要时可以明显超过 50 页。章节页数不得依靠空白、重复话术、放大字号、稀疏图表、冗长目录、练习或答案凑足。
- “扩充”必须同时增加机制深度、具体结构、状态变化、边界条件、失败路径和图示解释；只增加两三页、名词、概览或宽泛结论不算完成。
- 每章形成连续的因果主线，而不是彼此孤立的小百科条目。每节开头都要承接当前问题，结尾要明确得到的能力与尚未解决的限制。
- 第一章必须由一个带具体输入、地址、寄存器初值和预期结果的任务贯穿；采用“程序员可见现象—机器中的字节与状态—逐步执行证据—系统边界”的成书叙述，不得写成器件清单、三段式定义或扩写提纲。清单只能在连续推导后用于复核，不能承担正文主线。
- 优化必须在基本结构正确之后推导：先指出基本方案在哪种规模、并发、延迟或故障条件下出现具体代价，再引入索引、缓存、批处理、并行或日志等优化；不得把优化结构作为无来由的名词直接列出。

## 具体结构与状态

- 每个核心机制至少交代：输入与前置状态；参与对象和字段；对象之间的引用或所有权；数据路径；控制决策；等待与唤醒；提交点；可见结果；失败、回滚、重试或恢复。
- 不能只写 `task`、inode、超级块、文件对象、VMA、PTE、请求队列等名称。要说明对象中保存的代表性字段、字段来源、字段变化时机以及为什么不能由另一个对象替代。
- 对一次保存、切换、装载、映射、I/O 或权限检查，必须给出“之前有什么—保存了什么—由谁保存—保存在哪里—何时切换—恢复什么—按什么顺序恢复—何处才算完成”的完整过程。
- 区分相邻但不同的边界：请求/接受/完成/持久化，身份/执行现场，文件描述符/打开文件对象/inode，路径名/目录项/持久对象，策略/当前映射/物理归属，系统调用入口/调度/上下文切换/地址空间切换/返回用户态。
- 具体结构可以采用教学化字段集，但必须标明哪些是稳定语义、哪些是某类实现的代表性组织，避免把一个版本或一个架构的布局误写为唯一标准。

## 操作系统与硬件书的分工

- 本书是操作系统书。硬件原理已有对应书籍，不单设冗长硬件导论。
- 样本书的逻辑起点先用简洁篇幅说明最小无 OS 机器的整体结构：有哪些必要器件、器件怎样连接、一次取指或读写怎样沿连接完成。不得只给处理器和内存两个方框，也不得在连接尚未解释时直接使用“总线”“中断”等名称。
- 每次演进新增一种硬件时，必须依次交代三层含义：硬件模型（内部最小状态、输入、输出和状态变化）；软件模型（软件能读写的寄存器、地址、事件与操作顺序）；抽象（上层可以依赖的稳定能力及其不保证的事项）。同时说明新硬件接到机器的哪里、通过什么请求或信号与现有器件交互。
- “硬件模型—软件模型—抽象”只在硬件首次加入机器时完整展开；后续章节引用已建立的硬件能力时简洁复用，避免重复硬件书内容。
- 特权级、寄存器、页表、中断、DMA、Cache 等硬件事实只在当前内核机制需要时作为接口条件简要说明；重点放在内核如何组织对象、状态、并发、权限和恢复。
- 不在正文讨论源文件位置、仓库路径、编译命令、构建手段、检查脚本或内部编辑过程。代码示例直接讲语义、状态和执行过程。

## 语言与叙述

- 使用正式、准确、自然的教材措辞；用明确主语和机制动词表达因果。
- 禁止用“逼出”“逼出来”“吃掉”“喂给”“兜底”“饿死”“一招”“随手”“硬扛”“翻车”“死磕”“挨打”“遮羞布”等口语、强迫或暴力隐喻替代技术解释。
- 避免连续使用相同模板，如反复出现“先看一个问题”“本质上”“这说明”“由此可见”“换句话说”“需要强调的是”。过渡必须来自前后机制之间的真实因果关系。
- 一个段落承担一个中心问题；一个句子尽量只承载一个主要因果断言。先写具体主体，再使用“它”“这一步”等代词。
- 术语首次出现时给出中文名称及常用英文名或缩写，之后保持一种写法。不要为追求文采而随意更换技术名词。
- 不向读者暴露“用户要求”“扩写计划”“旧稿”“检查流程”“页数指标”等编辑信息。
- 在协作过程中，每进入一次新的演进阶段，先向用户报告：当前机器已经具备什么、出现了哪个具体问题、本阶段准备引入什么；样本书获得用户确认前，不把其结构直接迁入现有书籍。

## 图、表与版面

- 图是可验证的技术陈述，不是装饰。附近正文先提出具体问题，再由图解释结构、顺序、所有权或边界，图后给出可以据图推出的结论。
- 对象关系用结构图，状态前后差异用快照，多个主体随时间变化用泳道或时间线，嵌套与栈布局用分层图；不要用拥挤的节点云。
- 图中文字、节点、箭头和边界之间保持宽松间距。连线不得穿过文字或节点，不得无意义交叉、重叠或回绕。内容过多时分图，不以缩小字体掩盖拥挤。
- 所有正文表格要有清晰、连续、在手机尺寸仍可辨认的横线和竖线。长表按语义拆分并重复表头，前后用正文说明如何阅读；不要让连续页面只剩表格。
- 表格只承载真正需要行列对照的内容。过程推导、练习和答案使用连续正文或编号环境，不塞入超长表格。
- 版式参考《硬件从零到整机》的成熟风格：层级明确、正文密度稳定、图形留白充分、表格边界清楚，但不复制硬件书的内容组织。

## 练习与教学闭环

- 章末练习独立编号，至少覆盖概念解释、对象/字段追踪、完整 trace、边界条件、并发或故障定位；参考答案说明推理和状态变化，不只给结论。
- 练习与答案不计入 50 页有效正文基线。正文必须先完整教授练习所需机制。
- 例子要携带具体初值、对象、字段、事件顺序或错误码，使读者能够逐步复算，而不是只有抽象描述。

## 验收、导出与发布

- 修改前后都要测量章节在成品 PDF 中的有效正文页范围，报告实际增量；页数不能替代内容审计。
- 发布前检查输入可达性、交叉引用、术语、禁用措辞、重复模板、表格、图形、越界框、缺字、练习答案和 PDF 实际页面。
- 每张新增或修改的图都要渲染到最终 PDF 后目视检查。抽查章节开头、结构密集页、表格页、跨页过渡和章末。
- 完成修改后，除非用户明确取消：生成最终 PDF，导出到 `/mnt/sdcard/STU/BOOKS/按卷类型/原理卷/操作系统第一册`，核对源 PDF 与手机 PDF 哈希。
- 正式《操作系统第一册》和《操作系统演进样本》必须作为两个独立 PDF 并存于上述同一手机目录。导出任意一本时都要保留并核验另一本；不得调用会清空整个目标目录的单书导出流程。
- 只暂存操作系统书和本技能的相关文件，保留无关工作树内容；提交当前分支、推送已配置远端，并验证本地与远端分支 tip 一致。
