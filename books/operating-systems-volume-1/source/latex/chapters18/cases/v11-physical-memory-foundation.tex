\section{案例 v1.1（实现中）：让物理页、字节块、固定对象与虚拟区间都拥有生命周期}
\label{case:v11-physical-memory}

\begin{statebox}
\textbf{状态边界。} 项目当前发布基线仍是 v1.0；v1.1 已由 ADR 接受并实现五项增量。
ADR 0017 建立动态页帧元数据、高半区物理直映和 64 GiB QEMU 容量路径；
ADR 0020 把 64 KiB 高半区单调堆升级为可释放、可合并并能完整校验的通用堆。

精确释放。ADR 0023 再在通用堆上建立固定尺寸类型缓存，以活动位图和槽内

接受这五项增量；但 CMake 工程元数据仍为 v0.11，动态内核栈和空中间页表回收

“v1.1 已经发布完成”。
\end{statebox}

v0.6 已经能解析 E820 内存图，却只管理 Stage 1 恒等映射覆盖的低 64 MiB。
这在当时是一条安全边界：页表代码可把低端物理地址直接当作同值指针使用，
页帧状态也只需一份固定数组。进入 v1.1 后，QEMU 的 E820 可以报告 64 GiB
可用 RAM；若内核仍输出 64 MiB 的 managed bytes，问题并不在“机器没有内存”，
而在软件把\emph{启动时能直接访问的范围}误当成了\emph{长期能够管理的范围}。

\subsection{四个上限回答的是四个不同问题}

决定物理内存容量时，至少要区分下列四个边界。把它们压成一个
\code{memory\_size}，会使越界、地址洞和页表覆盖错误无法定位。

\subsection{两位页帧状态为什么仍可能需要四 MiB 以上}

页大小为 4096 字节，每字节容纳四个两位状态。若没有地址洞，64 GiB RAM
包含
\[
  \frac{64 \times 2^{30}}{2^{12}} = 2^{24}
\]
个页帧，最少需要 \(2^{24}/4=2^{22}\) 字节，即 4 MiB 状态存储。
但元数据下标是 PFN，不是“第几个可用页”。若 3 GiB 可用区之后有 1 GiB 洞，
高端 RAM 再延伸到 65 GiB 物理地址，那么状态数组必须覆盖洞后的 PFN，实际
尺寸会略大于 4 MiB；当前 64 GiB QEMU 主规格计算出的状态存储为
\code{0x410000} 字节。洞对应的状态保持 Unavailable。反过来，高端保留设备
窗口只要不包含可用 RAM，就不能仅凭自身端点把状态数组扩大到该窗口。

v0.6 的固定 4096 字节数组恰好只能表达低 64 MiB：
\[
  4096\ \text{B}\times 4\ \text{frames/B}\times 4096\ \text{B/frame}
  =64\ \text{MiB}.
\]
因此，仅把 \code{MANAGED\_BYTES} 常量改成 64 GiB 会让数组越界。v1.1 先根据
managed limit 计算元数据尺寸，再从低 64 MiB 的可用区间中寻找一段连续、
页对齐且不与固件、Stage 1、内核、BootInfo、启动栈及临时缓冲重叠的空间。
若找不到，启动必须明确失败，不能静默退回较小容量。

\begin{lstlisting}
prepare_physical_memory(e820, boot_objects):
    // 容量同时受固件事实、处理器可表达范围和直映窗口约束。
    cpu_limit = physical_limit_from_cpuid()
    map_limit = direct_map_capacity()
    managed_limit = align_down(min(highest_usable_end(e820),
                                   cpu_limit, map_limit), PAGE_SIZE)

    // 两位状态按 PFN 编号，地址洞也占据索引，但初始保持不可用。
    metadata_bytes = align_up(ceil(page_count(managed_limit) / 4),
                              PAGE_SIZE)
    metadata = find_low_identity_mapped_range(
        e820, boot_objects, metadata_bytes, PAGE_SIZE)
    if metadata does not exist:
        return FRAME_STATE_STORAGE_UNAVAILABLE

    // 先把全部状态置为不可用，再只开放合法 E820 type 1 页。
    initialize_frame_ledger(metadata, managed_limit, default=UNAVAILABLE)
    mark_type1_pages_free(e820)
    reserve_boot_objects(boot_objects, metadata)
    return SUCCEEDED
\end{lstlisting}

\subsection{direct map 提供访问路径，不授予页帧所有权}

新直映窗口起于 \code{0xFFFF888000000000}。对一个被纳入直映的物理地址
\(p\)，内核使用
\[
  v=\mathtt{0xFFFF888000000000}+p
\]
得到可解引用的高半区虚拟地址。页表项仍保存 \(p\)，CR3 仍要求物理地址；
只有 C++ 代码准备读写页表帧、清零用户页或复制 ELF 段时，才把物理地址转换成
当前地址空间中的虚拟地址。

这条规则消除了 v0.6 中隐含的
\code{reinterpret\_cast<void *>(physicalAddress)}。在旧 CR3 下，页表管理器
使用“虚拟基址为 0、只从低 64 MiB 分配页表帧”的访问策略；激活新 CR3 后，
同一管理器切换为“虚拟基址为 direct-map base、可访问全部受管物理页”的策略。
算法仍处理物理页号，解引用方式则随控制权阶段改变。

直映只覆盖完整的 E820 type 1 RAM，权限为 supervisor、read/write、NX 和普通
缓存。对齐且完整落在可用区间内部的部分优先使用 2 MiB 大页，区间边界与尾部
使用 4 KiB 页。保留区、未知区和 MMIO 不会因为落入窗口范围而自动变成普通
缓存 RAM；例如 LAPIC 仍由独立的 cache-disabled 映射处理。

\subsection{为什么换 CR3 必须是一笔启动事务}

新页表本身也需要物理页。只要处理器还在 Stage 1 的旧 CR3 下，内核就不能解引用
64 MiB 以上新分配的页表帧；因此建表阶段的分配上限必须暂时保持在恒等映射窗口。
待新根同时包含低端启动映射、内核映像、高半区直映、早期堆、保护测试页和
设备映射，并且所有步骤都成功后，内核才能写 CR3。

在 64 GiB 主规格上，目标机还要从 4 GiB 以上分配一个页帧，查询对应直映叶项，
确认它是 supervisor、writable、NX、普通缓存，然后通过高半区地址写入并读回
两个 64 位模式，最后释放页帧。这个测试同时证明“高端 PFN 已进入分配器”“页表
确实采用了该映射”“处理器实际能够读写”“释放后所有权返回”四件事；只打印
managed bytes 不能替代它。当前主规格要求高端自检物理地址不低于
\code{0x0000000100001000}，并以 32768 个 2 MiB 叶项覆盖对齐的 RAM 内部区间；
边界与洞由 4 KiB 叶项和 not-present 区间分别表达。

\subsection{为什么 buddy 的 order 是地址结构，不是任意编号}

单页扫描只能回答“有没有一页可用”，无法有效回答“有没有一段对齐的连续页”。
当前工作树把一个连续块写成 \code{PhysicalFrameBlock\{physical\_address,
order\}}。若页大小为 4 KiB，则 order \(k\) 的含义完整展开为
\[
  \text{frame count}=2^k,\qquad
  \text{block bytes}=2^{k+12},\qquad
  \text{start PFN}\bmod 2^k=0.
\]
最后一项不是为了让地址好看。只有块头按自身大小对齐，同阶块才拥有唯一伙伴：
\[
  \text{buddy PFN}=\text{block PFN}\mathbin{\mathrm{xor}}2^k.
\]
例如 order 3 表示八页、32 KiB，起始 PFN 的低三位必须为零；异或
\(2^3\) 只翻转其上的伙伴选择位，低三位仍为零。若允许任意长度或任意起点，
“相邻空闲区”可能属于另一个父块，释放时便不能仅凭地址确定能否合并。

order 变化时没有页面字节被搬到新地址。分裂只是把一个高阶空闲块的位图事实改成
一个继续分裂的半块和一个放回空闲集合的半块；合并则做相反的元数据变化。块覆盖的
物理地址始终不变。只有调用者随后通过 direct map 读写页面，页面内容才真正变化。

\subsection{为什么元数据先保留，buddy 初始化后不再追加保留区}

页帧状态存储和 buddy 位图都占用真实 RAM。内核先计算两者尺寸，在低端恒等映射
可访问区中寻找一段连续空间，再把前半段交给两位 PFN 账本、后半段交给 buddy
位图。接着初始化逐页账本，保留固件、Stage 1、内核、BootInfo、启动栈、临时
缓冲和这段元数据自身；只有所有保留成功后，才从最终 Free 页生成各阶空闲块。

这个顺序解释了两个看似严格的拒绝。第一，buddy 初始化前若已经存在普通分配，
仅凭 Allocated 页无法恢复它原来的块头和 order，因此
\code{InitializeBuddy} 返回“已有分配”而不是猜测。第二，buddy 初始化后，
\code{ReserveRange} 会返回“初始化后禁止保留”；否则逐页账本已经把某页改成
Reserved，各阶 Free 位图却可能仍把包含它的父块列为空闲。未来可以实现“先拆除
覆盖该区间的空闲块，再事务化保留”的接口，但当前阶段选择冻结保留集合，使两层
状态只有一条可审计的初始化路径。

对 \(N\) 个受管 PFN，每一阶分别保存 Free 与 Allocated 两族位图，原始尺寸为
\[
  M(N)=2\sum_{k=0}^{\lfloor\log_2N\rfloor}
  \left\lceil\frac{\left\lceil N/2^k\right\rceil}{8}\right\rceil
  \text{ bytes}.
\]
前面的 2 来自两族位图，不是“留一倍保险”。仅有 Free 位图无法识别一次释放
携带的 order 是否等于原申请；Allocated 位图正是错阶、错位和重复释放的证据。
纯 64 GiB、4 KiB 页的容量测试得到 \(8\,\mathrm{MiB}+4\) 字节原始尺寸；
主 QEMU 规格的 PFN 下标还覆盖 3--4 GiB 地址洞后的 65 GiB 物理端点，因此
页对齐后的目标机输出为 \code{BUDDY\_STORAGE\_BYTES=0x821000}。地址洞不会
变成 Free，但仍占据按 PFN 编号的位图位置。

代码把通用上限写成 order 51，也不是假定机器拥有 \(2^{51}\) 页。一个 64 位
半开物理地址范围最多表达 \(2^{64}\) 字节；4 KiB 页已经占去 12 位，因此
order 52 会代表 \(2^{52}\) 页、恰好 \(2^{64}\) 字节，其独占终点无法装入
\code{uint64\_t}。order 51 是仍可安全移位并表达完整块范围的最大阶。运行时还会
取 \(\lfloor\log_2N\rfloor\) 与 51 的较小者；当前 65 GiB 地址跨度只得到
\code{BUDDY\_MAX\_ORDER=0x18}，即 order 24，而不是为不存在的更高阶建立块。

\subsection{为什么目标自检申请 order 3，又为什么地址不是常量}

目标机自检申请 order 3 的八页块，并分别通过 direct map 写读首尾页。单页测试
无法证明“中间七个页边界都属于同一连续块”，过大的高阶测试又会人为提高最低内存
要求；八页、32 KiB 是一个能触发真实分裂与合并、同时保持启动成本有界的选择。
释放以后，自检要求 Free、Allocated、Reserved 页数恢复，活动块数恢复，成功
申请与释放各增加一次，并让 \code{ValidateBuddy} 全量通过。

范围下界是 \code{0x0000000100001000}，即 4 GiB 再加一页。加这一页是为了证明
结果严格位于 32 位地址上界之外，而不是刚好落在边界；分配器还会把候选起点向上
调整到 32 KiB 块对齐。当前 64 GiB 主规格实际得到
\code{BUDDY\_SELF\_TEST\_ADDRESS=0x0000001000000000}。这个地址由 E820 空闲区、
启动保留、此前页表分配、范围和 order 共同筛选，不是代码固定的设备地址或 ABI。
换一份内存图仍可返回其他合规地址，测试只要求整个八页块落在半开范围内且保持
order 3 对齐。

宿主单元测试验证 64 页模型的拆分、合并、错阶、错位、重复释放和失败原子性；
生命周期测试加入 E820 地址洞、保留区与高地址半开范围；固定种子随机测试在
1024 页模型中执行 \(100000\) 次 order 0--7 混合申请释放，每 257 步全量复算
位图不变量。三项新增测试把完整套件从 \(77\) 项推进到 \(80\) 项；本次完整构建、
ELF/固件审计和真实 QEMU 路径均通过。

\subsection{从单调指针到可回收字节块}

物理直映只解决“内核怎样解引用一个已经映射的物理页”，并不解决页上对象何时
死亡。v0.6 的堆只保存下一个空闲地址：每次分配向高地址推进，失败时返回容量
不足，却没有合法的释放操作。这样的单调堆适合与内核同寿命的启动对象；若
Thread、FileTable 或动态内核栈沿用它，对象退出只会留下无法复用的字节。

当前 \code{KernelHeap} 仍使用原有 64 KiB RW/NX 高半区，但每个物理块增加
48 字节块头，保存自身长度、前块长度、请求长度、状态签名和双向空闲链接。
自身长度与前块长度构成边界标记，使释放路径能够直接找到相邻块；空闲块另按
地址递增进入双向链表。分配先遍历完整空闲集合，选择能容纳请求的最小块，再
计算对齐前缀与剩余后缀；所有边界和溢出检查通过以后，才一次性提交分裂结果。

并发、zone、迁移类型与回收水位；当前类型缓存负责固定尺寸对象的单后备块，
KVA 已负责虚拟区间所有权。通用堆不能替代这些层次。

\subsection{为什么通用堆之上还需要固定尺寸类型缓存}

通用堆已经能够释放和合并，继续让每个 64 字节内核对象单独调用它，看起来似乎
最省设计工作。但通用堆不知道下一个请求的尺寸和对齐：每次申请都要搜索
best-fit 候选、计算前缀与后缀并携带块头；大量同尺寸短寿命对象还会把空闲区
切成许多不同形状。类型缓存利用一条额外事实——同一缓存中的对象尺寸与对齐
相同——在初始化时一次性排好槽位，之后取得和归还都只改链头、位图与计数。

当前实现故意先取固定容量、单后备块，而不是直接实现多 slab 的 SLUB。这样做
使一份缓存只有一个来自 \code{KernelHeap} 的所有权根：初始化成功后整块归
缓存，所有槽归还并通过校验后，销毁再把同一块整体交还通用堆。代价是容量耗尽
时只能明确返回 \code{OutOfObjects}，不能自动增长。KVA 现已能许诺扩展所需
虚拟区间，但页表回收、多 slab 所有权和并发规则尚未具备，因此本增量仍不自动
增加后备块。

设对象原始尺寸为 \(s\)，对齐为 \(a\)，容量为 \(N\)。后备布局由下列五个量
唯一决定：
\[
\begin{aligned}
  B &= \left\lceil N/8 \right\rceil, &
  A &= \max(a,8),\\
  S &= \operatorname{align\_up}\!\left(\max(s,8),A\right), &
  O &= \operatorname{align\_up}(B,A),\\
  H &= O+N S.
\end{aligned}
\]
\(B\) 是活动位图字节数；\(A\) 是后备块和对象区所需对齐；\(S\) 是相邻槽
起点间距；\(O\) 是对象区相对后备块起点的偏移；\(H\) 是向通用堆申请的总
字节数。这里的两个 8 都来自空闲槽要保存一个 64 位“下一槽索引”，不是在暗示
所有内核对象至少有 8 字节。即使对象只有 1 字节，空闲状态仍须容纳链节点；
对象一旦活动，整个槽才全部归调用者。尺寸乘法、对齐加法和总长加法都在调用
通用堆以前检查溢出，因而错误配置不会留下半个后备申请。

\subsection{位图与槽内链为什么不是重复记录}

只有空闲链时，取得链头可以做到 \(O(1)\)，却无法回答传入地址当前是否仍由调用者
持有。第一次归还会把槽压入链；若第二次归还同一地址，单链结构本身不能可靠区分
“合法空闲槽”和“重复提交的活动槽”，结果可能让同一地址在链中出现两次，随后被
交给两个所有者。只有活动位图时可以拒绝重复释放，却需要扫描才能寻找空闲槽。
因此两份记录回答不同问题：位图是每槽活动所有权的独立真相，链是空闲集合的
快速访问顺序。

链中保存索引而不是任意下一指针，也把可接受状态约束在
\([0,N)\cup\{\mathtt{UINT64\_MAX}\}\) 内。校验器可以从链头最多走 \(N\) 步，
遇到越界索引、活动槽或超过容量仍未到链尾，都立即报告损坏；最后还要把观察到的
空闲数与位图观察到的活动数、缓存计数逐项核对。LIFO 不是公平性契约，它只是让
归还成为常数时间压栈，并优先复用刚访问过的槽；调用者不能依赖特定的长期顺序。

\begin{longtable}{|L{0.18\linewidth}|L{0.27\linewidth}|L{0.30\linewidth}|L{0.15\linewidth}|}
\hline
\rowcolor{BookBlueTint}
\textbf{操作} & \textbf{提交前验证} & \textbf{唯一提交点之后的变化} &

\endhead

归还操作会把该槽首 8 字节改写为空闲链索引。这不是保存对象内容，也不是把对象
搬到链表节点；它表示调用者的对象生命周期已经结束，该存储现在由缓存重新解释。
因此归还以后继续读取旧字段属于 use-after-free。相反，取得时只保证返回一段满足
尺寸与对齐的原始存储，不负责清零，也不隐式执行 C++ 构造函数；模板
\code{KernelTypeCache<ObjectType>} 目前只用 \code{sizeof}/\code{alignof}
提供类型化指针。对象构造、析构、poison、redzone 和引用计数都属于更高层契约。

\subsection{为什么代表案例得到 \code{0x840}，而不是把它写成常量}

目标自检选择尺寸 \(s=64\)、对齐 \(a=64\)、容量 \(N=32\)。64 字节对象能够
明确检查 cache-line 对齐和首尾字段写回；32 槽足以完整耗尽、交错归还并再次
复用，同时把启动自检成本限制在固定范围。它们是代表案例的输入，不是所有未来
类型缓存必须遵守的 ABI。

代入布局公式可得
\[
  B=\lceil32/8\rceil=4,\quad A=64,\quad S=64,\quad
  O=\operatorname{align\_up}(4,64)=64,
\]
于是位图之后有 60 字节对齐填充，总后备长度为
\[
  H=64+32\times64=2112=\mathtt{0x840}.
\]
\code{0x840} 因而是尺寸、对齐与容量的派生结果。若对象只有 1 字节、对齐为
1、容量为 9，当前规则会得到 2 字节位图、8 字节对象区偏移、8 字节槽步长和
80 字节总长；单元测试专门覆盖这个非整字节位图案例，防止实现只对 32 槽偶然
成立。

目标机依次取得全部 32 槽并写读首尾模式；第 33 次取得必须返回耗尽且不改输出
指针。随后先归还偶数槽、尝试一次重复归还并要求拒绝，再归还奇数槽；此时最后
归还的槽 31 位于 LIFO 链头，下一次取得必须复用同一地址。再次归还并销毁后，
累计成功取得与归还均为 33，峰值为 32，活动数为 0，空闲数为 32；通用堆的
当前占用、活动申请与最大空闲负载还要恢复到进入自检前的基线。

宿主单元测试补充无效配置、布局溢出、后备堆不足、内部/外部指针和活动对象销毁；
集成测试让 8、64、256 字节对齐的三个缓存共享 64 KiB 通用堆，交错释放时核对
其余缓存的活动数据，最终乱序销毁并恢复单一连续空闲区；固定种子随机测试执行
\(100000\) 步申请与归还，每 257 步用独立记录核对地址唯一性、数据模式、位图、
空闲链和统计。三项测试把完整套件由 80 项推进到 83 项，本次完整构建、产物审计
与真实 QEMU 路径均通过。

当前缓存仍由 BSP 启动路径或调用者串行化，不提供内部锁，也不允许把
IRQ、NMI 或 panic 路径当作安全调用环境；它只有一个固定容量后备块，没有
空/部分/满 slab 列表、per-CPU 快速路径和内存压力回收。这些限制说明 ADR 0023
闭合的是“固定尺寸存储的最小可回收生命周期”，不是宣称现代 slab 分配器已经
完成。

\subsection{为什么 not-present 不能表示“这段虚拟地址无人拥有”}

物理页分配器已经知道哪些页帧属于谁，页表也能回答某个虚拟页当前是否存在翻译。
看起来只要扫描 not-present 页，就能找到一段“空闲虚拟地址”。问题在于
not-present 只是一条硬件翻译事实，不是一条软件所有权事实。动态内核栈会取得
“首 guard + 若干栈页 + 尾 guard”的完整区间，却故意让两个 guard 没有叶项；
映射事务还可能先许诺地址，随后才逐页取得物理后备。若另一个调用者把这些
not-present 页当成空闲地址，保护页就会在没有任何页表冲突的情况下被重复分配。

因此当前项目把一次动态映射拆成三份彼此不能代替的记录：

显式清零、写入或复制页内容时，后备字节才真正变化。

\subsection{为什么 KVA 从 \code{0xFFFFC90000000000} 开始}

这个常量既不是处理器规定的 vmalloc 地址，也不是从宿主 Linux 借来的现成映射。
当前四级分页把高半区物理直映放在 \code{0xFFFF888000000000}，为它保留
64 TiB；该窗口的独占终点为 \code{0xFFFFC88000000000}。项目再留出
512 GiB 的完整 PML4 槽位作为布局间隔，于下一个槽位
\code{PML4[402]} 的起点建立 KVA：
\[
\begin{aligned}
  \mathtt{KVA_{begin}} &= \mathtt{0xFFFFC90000000000},\\
  \mathtt{KVA_{size}}  &= 32\ \mathrm{TiB}
                         =\mathtt{0x0000200000000000},\\
  \mathtt{KVA_{end}}   &= \mathtt{0xFFFFE90000000000}.
\end{aligned}
\]
32 TiB 恰好跨越 64 个 512 GiB PML4 槽位，即 \code{PML4[402..465]}；
起点和最后一个字节都符合当前 48 位 canonical 规则。选择整槽边界使页表层次、
容量和冲突检查可以直接复算，也为 direct map 与 KVA 之间保留明显的诊断边界。
若未来启用五级分页，地址即使仍然 canonical，也不能悄悄沿用；谁解释地址的
规则已经改变，必须由新的布局决策迁移。

最后一行区分了“区间数量”和“页容量”。一个描述符保存起始地址、页数和类型，
既可以代表一页，也可以代表数十亿页；256 限制的是同时活动的 allocation 与
reservation 总数。若按 32 TiB 窗口每页保存一位，仅一族位图就要
\(2^{33}/8=1\) GiB；再区分保留与分配还会继续增长。当前启动期只有少量区间，
用 6 KiB 描述符数组换取 \(O(N)\) 扫描，是有意识的规模选择。

\subsection{为什么只记录有主区间，空闲区间却不用合并}

\code{KernelVirtualAddressRangeDescriptor} 数组只使用前部活动元素，并按
起始地址严格递增；每项类型为 Allocation 或 Reservation，尾部必须全部保持
Unused、零地址和零页数。窗口起点、相邻描述符终点与下一个描述符起点之间的
缝隙就是空闲区间。删除一个 allocation 描述符以后，左右缝隙在数学上立即成为
一个更大缝隙，不需要再修改空闲链或执行显式合并。

申请使用 best-fit，但对齐的是\emph{绝对虚拟页号}，不是“从窗口起点数第几页”。
若请求八页对齐，成功地址自身必须是 32 KiB 的倍数；换一个不满足同样对齐的
窗口基址时，相对偏移八页对齐并不能替代这条要求。实现先遍历全部缝隙、计算对齐
候选，再选择原始页数最小的可容纳缝隙；同样大小保留低地址候选。所有乘法、向上
对齐和末端加法都在移动描述符以前检查，因此失败不会留下半次插入。

\begin{lstlisting}
try_allocate_kva(request_pages, alignment_pages, output):
    // 页数必须非零；对齐页数必须为二次幂，才能用掩码安全对齐。
    validate_request_without_changing(output)

    best = none
    for each gap derived from sorted owned descriptors:
        // 对齐绝对页号，保证最终虚拟地址本身满足硬件/调用方要求。
        candidate_page = align_up(gap.begin / PAGE_SIZE,
                                  alignment_pages)
        // 先证明候选半开区间仍完整落在当前 gap 中。
        if candidate fits request_pages:
            // 选原始 gap 最小者；扫描顺序自然保留同尺寸低地址候选。
            remember_candidate_if_better(best, gap, candidate_page)

    if no candidate:
        // 地址耗尽与描述符耗尽是两种压力，错误码不能混写。
        return OUT_OF_VIRTUAL_ADDRESS_SPACE

    // 到这里才移动数组尾部、插入描述符并更新守恒计数。
    commit_descriptor_and_statistics(best)
    output = exact_range(best, request_pages)
    return SUCCEEDED
\end{lstlisting}

Reservation 与 Allocation 共用页对齐、窗口边界和重叠验证，但保留区不能通过
\code{TryRelease} 释放。普通释放也不接受“范围里任意一个地址”：它必须同时
匹配活动 allocation 的精确起点和原始页数。内部地址、错误页数、保留区与重复
释放分别得到可区分的错误，并且都不移动数组或修改计数。这样，释放接口不会猜测
调用者原本拥有哪个对象。

\subsection{为什么六页自检以前还要先映射一页}

当前 \code{UnmapPage} 能清除叶项并执行 \code{INVLPG}，却尚不回收已经变空的
PML4 以下中间页表。第一次在 KVA 槽位建立 4 KiB 映射，需要新建 PDPT、PD 和
PT 三页。如果把这三页混入主生命周期的前后统计，就会把“当前已知的页表基础
设施成本”误报成数据页泄漏。项目先申请、映射、写读、撤销并归还一页作为暖机；
这段事务归还数据页和 KVA 区间，却有意把三张中间表留作随后测试的基线。

暖机取得窗口第二页 \code{0xFFFFC90000001000}，因为首页已经永久保留。主事务
随后申请六页并要求八页对齐。窗口基址本身按八页对齐，但从第二页开始的空洞要
向上越过七页前缀，故结果必为
\[
  \mathtt{0xFFFFC90000000000}+8\times4096
  =\mathtt{0xFFFFC90000008000}.
\]
这不是写死的“栈地址”，而是永久保留、绝对对齐和 best-fit 共同推导出的当前
测试结果。六页中第 0 与第 5 页保持 not-present，中间四页映射到一个 buddy
order 2 连续块：

主事务成功后，累计申请与释放都为 2：一次来自暖机，一次来自六页主测试；
峰值为 6，活动分配页为 0，永久保留页为 1，活动描述符只剩首页 reservation。
窗口总计 \(2^{33}\) 页，所以最终空闲页和最大连续空洞都为
\(2^{33}-1=\mathtt{0x1FFFFFFFF}\)。单元测试覆盖 best-fit、绝对对齐、两类
耗尽、错误释放和外部元数据损坏；集成测试串联真实页帧与页表；固定种子随机
测试在 512 页独立逐页模型上执行 \(100000\) 步，并每 257 步复算统计和最大
空洞。三项测试把完整套件由 83 项推进到 86 项，完整构建、ELF 审计与真实
QEMU 路径均通过。

本轮审计也保留了一次有解释力的失败：初始 64 GiB 系统测试在 15 秒边界只通过
85 项，串口停在内存初始化以前的最后一个里程碑。异常跟踪没有出现新的处理器
故障；原因是 Debug 路径要扫描 \(16777216\) 个页状态，旧墙钟预算与正常运行
时间过于接近。项目随后把普通配置保持为 15 秒、64 GiB 主规格调整为有界的
40 秒，CTest 再以 50 秒设外层上限，并为预算选择补单元测试；调整后的首次
重跑约 12 秒完成，最终提交复验约 16 秒完成，86 项均全部通过。这里调整的是
宿主观察预算，不是放宽来宾里程碑、跳过 KVA 校验或把超时当成功。

当前 KVA 仍要求 BSP 启动路径或调用者串行化，扫描、插入和删除最多 256 个
描述符，尚无锁、平衡树、per-CPU 地址缓存或延迟 TLB 批处理。它只管理地址，
不替调用者取得物理页、建立映射或自动回滚跨层事务；动态内核栈尚未迁移，
空中间页表也尚未回收。启动自检任何失败都会停止系统；未来运行时调用者则必须
把“全部 unmap 成功”作为归还物理页的前置提交条件，不能让仍可命中的旧翻译
指向已经复用的页。

因此，direct map 不是 \code{kmalloc}，buddy 也不是字节对象分配器，边界标记堆
不是类型缓存，当前单后备块类型缓存也不是完整 SLUB，KVA 也不是页表映射器。
当前四个 PCB、内核栈和
描述符容量尚未动态化，堆后备区与类型缓存都不会按需增长。v1.1 的五项已接受
增量分别解除“内核只能看见低 64 MiB”“堆对象只能分配、不能归还”“只能逐页
扫描、不能恢复连续块”“同尺寸对象仍需反复经过通用堆”和“未映射地址无法记录
软件所有者”五条限制，为后续动态内核栈、对象表、COW 与按需分页建立可逐层
验收的资源通路。
