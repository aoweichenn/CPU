# 写作标准

本书每个算法都必须按同一标准扩写。正式书稿只写在 `source/latex/`，不维护 Markdown 正式版本。

规模目标为 18 万统计单位，统计口径是“中文汉字字符 + 英文单词”，代码块、命令、复杂度公式、终端输出和 LaTeX 标记不计入。这个目标用于约束内容深度，不能通过重复段落、堆代码或无解释题单凑数。

## 章节结构

每章至少包含：

1. 问题模型。
2. 暴力解。
3. 暴力解复杂度。
4. 暴力解慢在哪里。
5. 优化条件。
6. 优化解不变量。
7. C++20 代码。
8. 容器选择原因。
9. 边界和反例。
10. 力扣案例题单。
11. 面试表达模板。
12. 练习和复盘要求。

数据结构章节还必须包含底层表示、核心操作复杂度、C++ 容器或手写结构、迭代器/引用失效、典型算法应用和不适用场景。

## 代码要求

- 使用 C++20。
- 只读大对象用 `const T&`。
- 需要修改输入副本时按值传参，并在正文说明原因。
- 不写递归版作为唯一实现；需要递归思想时，同时说明栈深风险。
- 复杂度必须同时写时间和空间。
- 变量名要表达含义，例如 `left`、`right`、`prefix_count`、`fresh_count`。
- 避免把所有逻辑塞进一个超长函数。

## 讲解要求

不能只写“用哈希表优化”。必须说明哈希表保存什么、为什么查询这个 key、何时插入、重复 key 如何处理。

不能只写“用滑动窗口”。必须说明窗口不变量、右边界何时移动、左边界何时收缩、什么条件下窗口方法失效。

不能只写“用二分”。必须说明答案范围、`check` 函数和单调性。

不能只写“用 DP”。必须说明状态定义、状态转移、初始化、遍历顺序和空间优化条件。

## 案例题强制讲法

每个案例题都必须写出从暴力到优化的完整过渡，不能只贴最终代码或只说题型标签。最低结构如下：

1. 题目合同：输入、输出、约束、样例和答案对象是什么。
2. 暴力解：给出可信 reference 思路；核心案例必须给出完整代码。
3. 暴力过程：用样例列出暴力枚举的候选，例如每个窗口、每个区间、每个固定点或每个状态。
4. 浪费点：指出相邻候选或相邻状态之间重复做了什么。
5. 优化条件：说明题目给了什么性质，例如固定窗口长度、正数单调性、有序性、前缀代数关系、支配关系或重叠子问题。
6. 状态复用：把“上一个状态如何变成下一个状态”写成具体动作，例如删左加右、查历史 key、弹出被支配候选、更新 DP 表格。
7. 指针和字段含义：解释每个下标、指针、计数表、栈、队列、堆或 DP 值保存什么。
8. 优化代码：代码必须和上述状态一一对应，关键两三行要在正文里翻译成人话。
9. 样例走读：至少手算一个关键样例，展示状态如何变化以及答案何时更新。
10. 边界和坑：说明会打破错误写法的输入，不能只列名字。
11. 复杂度变化：明确暴力复杂度、优化后复杂度、空间复杂度，以及哪一层重复被消掉。
12. 迁移问题：说明条件改变时算法是否还能用，例如固定窗口改成变长、全正改成含负、字符集固定改成泛化字符集。

固定长度滑动窗口案例必须特别写清：窗口长度 `k` 从哪里来，第一个窗口如何统计，后续窗口每次哪个字符出去、哪个字符进来，当前窗口起点如何计算。使用 `unordered_map` 时要说明计数为 0 的 key 是否需要删除；使用 26 长度数组时要说明字符集假设。
